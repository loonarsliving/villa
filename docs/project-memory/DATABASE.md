## `walkin_payments` (added 2026-08-23 — Payment Gateway module)
Isolated table for the walk-in cafe/spa cashier module (`/front-desk/payment-gateway` — a shared feature for both `admin` and `receptionist`, relocated from `/admin/payment-gateway` same day): `id, guest_nama, guest_hp, kategori (cafe|spa|lainnya), deskripsi, jumlah, status (pending|lunas|batal), created_by, created_at, paid_at`. RLS enabled, no policies (service-role/`villa-api`-only access, same pattern as `sync_config`/`automation_config`). Reachable via `GET/POST/PATCH /walkin-payments` (renamed off `/admin/*` in villa-api v17, gated `isStaff` not `isAdmin`, so receptionist isn't blocked by the blanket admin-only path check). **Deliberately not fed into `transactions`/`computeReport`** — that stream drives the investor 70/30 revenue-sharing split for villa rental income, and cafe/spa walk-in income is a separate business line not covered by that split. `GET /report` surfaces a read-only `walkin_income: {cafe, spa, lainnya, total}` breakdown for the requested `periode`, computed by `computeWalkinIncome()` — shown to investors purely for transparency (not summed into `gross_revenue`/`net`/`owner_amount`).

## `walkin_qris` setting (added 2026-08-23)
The static QRIS image for the walk-in cashier is stored as a row in the existing `integration_settings` table (`key='walkin_qris'`, `value={data_url: "data:image/...;base64,..."}`). Originally read/written via the generic `GET/POST /admin/settings` endpoints; moved in villa-api v17 to dedicated `GET/POST /walkin-qris` endpoints (`isStaff`-gated) so receptionist can read/replace the QRIS image without gaining access to `/admin/settings`'s other integration secrets (cloudbeds, vercel_bridge, etc., even redacted). Client-side upload is capped at 1.5MB before base64 encoding to keep the JSON payload/jsonb column reasonable.

## Villa walk-in bookings via Payment Gateway (added 2026-08-23)
The Payment Gateway's "Villa" kategori (for guests who book directly, not via OTA/Cloudbeds) does **not** write to `walkin_payments` — it calls the real booking pipeline instead: `POST /bookings` when the QRIS is generated (status `terjadwal`, `sumber:'walk-in'`, same double-booking check as Front Desk), then `POST /checkin` on "Tandai Lunas & Check-In" (sets the unit `occupied`, inserts the `transactions` income row that feeds `computeReport`'s 70/30 split, sends the door-PIN WhatsApp message) — identical effects to the existing Front Desk Check-In flow, just initiated from this screen. Added `PATCH /bookings` (`{id, status}`, villa-api v16) so an unpaid walk-in booking can be cancelled (`status:'batal'`) without leaving a phantom hold on the unit's date range.

## Collective investor revenue share (added 2026-08-23, villa-api v17/v18)
Per explicit owner instruction: investor (`role=owner`) reporting is now villa-wide/collective, not per-unit — a unit is only a stay-rights token (12 nights/year outside high season), not the basis for revenue-share proportion. `/report`, `/transactions`, `/notifications` no longer force `unit_id = session.unit_id` for this role (they force it to `undefined` instead, ignoring any `unit_id` query param the older frontend code still sends). `computeReport()` adds `countActiveInvestors()` (count of `villa_users` with `role='owner' AND is_active=true` — 13 at last check, matching the 13-unit count 1:1) and `per_investor_amount = owner_amount / investor_count`. The pre-existing Rp 5,000,000/month minimum-guarantee check (`jaminan_aktif`/`jaminan_topup`) was corrected in v18 to compare against `per_investor_amount` rather than the whole `owner_amount` pool, since the guarantee is understood to apply per investor.

## Check-In Card: `bookings.ktp_photo_path` / `bookings.signature_data_url` + `guest-documents` bucket (added 2026-08-27)
Migration `add_checkin_card_ktp_signature`: two new nullable columns on `bookings` (`ktp_photo_path text`, `signature_data_url text`), set by `villa-api` v21's `/checkin` handler from the request body (`ktp_photo_path`, `signature_data_url`), alongside the existing `pin_kode`/`checkin_at` fields. Also created a new **private** Storage bucket `guest-documents` (`public: false`, same pattern as `attendance-selfies`/`memo-attachments`/`leave-attachments` in this shared project) — KTP/passport photos are sensitive PII and must never be publicly readable. Villa's own `/api/checkin/upload-ktp` route (service-role key, staff-gated) uploads to `guest-documents/ktp/<uuid>.<ext>` and returns only the storage path, which is what gets written to `bookings.ktp_photo_path` — the image itself never touches the `bookings` row. `signature_data_url` stays a small base64 PNG data URL directly in the column (same pattern as the existing `walkin_qris` static image), since a canvas-drawn signature is only a few KB, unlike a photo.
- **Tahap 1 only**: this is capture-and-store, no OCR/auto-read of the KTP yet, and no viewer UI was built to look at a stored photo/signature after the fact (out of scope for this round — flagged for the owner as a follow-up once OCR + a Mkhsistem/Filemanager bridge are researched, see INTEGRATIONS.md/CHANGELOG.md).

## Direct DB access pattern
Only the Cloudbeds webhook route (in this repo) touches Postgres directly (via `@supabase/supabase-js` with the service-role key, which bypasses RLS). All other reads/writes go through `villa-api`, which also uses the service-role key (confirmed above).
